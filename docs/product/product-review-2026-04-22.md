# 产品体验评审 2026-04-22

## 1. 评审范围

本次评审基于以下证据完成：

- 实际运行 `tools/demo_ai_inbox_flow.py`，覆盖 `default`、`triage`、`resolved` 三个场景。

- 运行当前测试并核验稳定性现状。

本评审采用两个视角：

- 机构交易视角：是否足够快、稳、可审、可控、可追责。
- 产品视角：是否形成清晰工作台、是否完成闭环、是否具备付费交付感。

## 2. 总结判断

### 2.1 当前产品阶段

当前产品已经明显超过“功能集合型桌面工具”，正在进入“决策工作台”阶段。

尤其是以下三件事已经成型：

- 壳层统一：总览、推荐、交易执行三页已经共享一套终端语言。
- 链路清晰：市场 -> 推荐 -> 送审/执行 -> 回执/复盘 的主路径是成立的。
- 可解释增强：主线、战法、风险、消息、AI 评测都在朝同一套表达收敛。

但如果按交付标准判断：

- 作为内部演示版：已可用。
- 作为专业个人版试收费产品：接近可试运行，但稳定性和默认交互仍不够硬。
- 作为机构级终端：距离还比较大，主要缺口不在 UI，而在风控、审计、权限、组合级执行和工程可验证性。

### 2.2 评分

- 产品定位清晰度：8/10
- 研究到推荐工作台完成度：7/10
- 推荐到执行闭环完成度：6.5/10
- 交易前风控与审查能力：5/10
- 组合级/机构级能力：3/10
- 工程稳定性与可追踪性：5/10
- 商业化交付感：6/10

## 3. 这版最强的地方

### 3.1 不是“看盘页堆功能”，而是有主控逻辑

从截图和代码结构看，产品已经不是传统行情终端那种“模块平铺”，而是试图把用户每天的处理路径固定下来：

- 总览页负责回答“今天能不能做、主线在哪、市场温度如何”。
- 推荐页负责回答“今天先看谁、为什么看、是否送审”。
- 交易页负责回答“能不能提、提完怎么看、失败后怎么办”。

这是对的，而且很重要。

### 3.2 推荐页的消息中心方向正确

这次最像产品而不是功能点的，是统一消息中心。

从 demo 结果看，你们已经把：

- AI 评测事件
- 消息源刷新事件
- 推荐池刷新事件
- 交易提交/回执事件

汇总到同一工作区里。这个方向非常对，因为专业交易用户最怕的是事件散落在多个页面。

### 3.3 执行页已有“审查中心”雏形

交易执行页已经不只是订单提交器，而是在向审查中心演进，尤其体现在：

- 有执行阶段
- 有委托队列
- 有回执状态
- 有执行指标
- 有人工复核与风险优先

这条路比单纯做“下单按钮”更适合商业化。

## 4. 当前最关键的问题

### 4.1 页面 headline 与默认主动作还没有完全对齐

这是本次体验里最明确的产品问题。

在实际运行 demo 时出现了下面的现象：

- `default` 场景中，摘要是 `AI评测失败 | 去配置补 Key`，但主按钮仍是 `去机会池复核`。
- `triage` 场景中，首行是 `交易/异常 | 龙头样本 提交失败`，但主按钮仍然停留在复核机会池。
- 只有 `resolved` 场景里，主按钮和异常类型才重新对齐。

这说明当前消息中心的：

- 头部摘要
- 当前选中事件
- 默认 CTA
- 动作提示

还没有完全被同一个优先级引擎统一。

这在交易产品里很危险，因为异常分诊时，默认动作就是用户行为。

### 4.2 第一屏“空状态占比”仍然偏高，完成度观感被拉低

总览页和推荐页的终端感已经不错，但第一屏里仍有很多“待图表 / 待价位带 / 待资金画像 / 等待市场快照”的占位表达。

这会带来两个问题：

- 用户第一次打开时，会觉得系统还在搭架子。
- 即使能力已经存在，也会被空状态冲淡成 demo 感。

建议把“缺数据”与“缺能力”彻底区分：

- 缺数据时，给样例态、缓存态、最近一次快照态。
- 缺能力时，才给占位提示。

### 4.3 工程稳定性信号不一致，影响产品可信度

这次核验里最不应该出现的，不是单个测试失败，而是“状态口径不一致”：

- `docs/STABILITY_SUITE_LATEST.md` 仍显示 `3.13 full tests: 292 (FAIL)`、`3.12 compatibility subset: 140 (FAIL)`。
- 但仓库里的历史单测日志又有 `380 tests OK`、`435 tests OK`。
- 我本次重新执行后，当前代码确实存在失败，不是纯历史遗留。

本次复测抓到的真实问题包括：

- `tests.test_core` 首个失败点原本落在 `current_strategy_budget_bias_map` 与执行复盘联动。
- 修复后，继续出现新的失败：`test_load_universe_folder_runs_local_scan`，原因是 UI 文案已经变更，但测试期望未同步。
- Python 3.12 兼容子集还出现了状态文件清理权限异常，说明资源释放/文件句柄管理还有隐患。

结论很直接：

- 当前不是“稳定性文档没更新”这么简单。
- 当前是“产品在持续进化，但回归口径和工程收口没跟上”。

### 4.4 交易前风控仍偏单票，距离机构级还差一个层级

现在系统已经有风险提示，但更多还是单票和单动作视角。

真正的机构级或半机构级交易终端，还需要前置回答这些问题：

- 这笔单会不会把组合打穿行业/题材集中度？
- 这笔单会不会让净风险暴露超阈值？
- 这笔单和已有持仓是否形成同向拥挤？
- 如果同一主题今天已经亏损，这笔单是否应自动降权？
- 如果市场进入退潮，是否应该直接切到“只减不加”模式？

这些问题必须在“送审前”就被结构化呈现，而不是等提交时再提醒。

### 4.5 机构化能力缺口不在界面，而在治理层

如果目标继续往机构端靠，当前缺失的重点能力包括：

- 多账户与账户分组
- 组合级暴露与限额
- 角色权限与审批链
- 操作审计与回放
- 失败订单二次审查队列
- Basket / 批量指令
- Kill switch / 一键冻结
- 交易后 TCA 与偏差归因

这类能力不会自然从推荐页长出来，需要单独作为一层治理系统建设。

## 5. 我认为最值得先做的五件事

### P0-1. 把“事件优先级 -> 默认动作 -> 路由页面”彻底统一

目标：

- 摘要在说什么，默认主按钮就做什么。
- 交易异常优先去交易页。
- AI 配置异常优先去配置页。
- 普通消息和复核事件再回推荐页。

验收标准：

- headline、首行事件、默认 CTA、action hint 四者一致。
- 不再出现“顶部提示去配置，按钮却去机会池”的错位。

### P0-2. 把第一屏从“空态页面”改成“可消费页面”

目标：

- 用户打开后 10 秒内，至少能看到市场快照、缓存快照或样例快照。
- 首页和推荐页默认不要堆太多“等待中”。

建议动作：

- 引入最近一次有效快照回显。
- 样例数据与真实数据双模式切换。
- 对总览卡片提供最小可消费 fallback。

### P0-3. 把交易页升级成真正的“提交前审查中心”

至少增加四类前置审查：

- 组合影响
- 主题集中度
- 风险预算占用
- 当前市场阶段适配

建议输出不要只给“能否提交”，而要给四档结论：

- 允许提交
- 建议缩量
- 延迟观察
- 禁止提交

### P0-4. 建立唯一可信的稳定性口径

目标不是“把测试跑过”这么简单，而是：

- 文档状态与真实状态一致
- 失败能快速定位到页面/模块/责任域
- 发布前能明确知道是“可演示”还是“可交付”

建议立即做：

- 稳定性总报告只由一套脚本生成
- 报告内附首个失败测试名与失败摘要
- 将 `3.13 full`、`3.12 compat`、`offscreen smoke`、`demo smoke` 分开报告
- 发布材料里强制附当前时间戳和 commit/工作区状态

### P1-1. 把主线引擎结果真正前置到所有页面

主线是你们最应该形成壁垒的地方。

建议尽快把以下字段变成统一的一等公民：

- `mainline_strength_score`
- `mainline_continuation_score`
- `mainline_switch_risk`
- `mainline_role`
- `execution_readiness`
- `mainline_window_score`
- `mainline_risk_flag`

然后在：

- 总览页
- 推荐页
- 个股详情页
- 交易审查页

全部使用同一口径表达。

## 8. 最终判断

如果你们当前目标是：

- 先做一个专业桌面终端，服务高频盯盘和短线决策用户

那方向是对的，而且已经有明显产品势能。

如果你们当前目标是：

- 直接把它卖成“机构级交易终端”

那现在最大的短板不是页面不够高级，而是：

- 默认动作优先级还不够稳
- 回归治理还不够硬
- 组合级风控还没真正立起来
- 权限、审计、账户治理层还没有成型

一句话结论：

这不是一个应该推倒重来的产品，而是一个已经具备工作台骨架、现在最需要“把默认行为、风控和稳定性做硬”的产品。
