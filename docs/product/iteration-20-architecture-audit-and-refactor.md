# 迭代 20 - 架构审计与可扩展性重构

## 目标

- 先从产品业务链路出发重新审视项目结构，而不是继续无节制叠功能。
- 找出当前最影响可维护性和扩展性的代码热点。
- 在不打断现有功能的前提下，优先做一轮低风险、高收益的结构性收敛。

## 当前业务主链

项目当前已经具备较完整的业务闭环：

1. `market_feed.py`
   - 接入东方财富与本地缓存
   - 生成市场快照、K 线、算法池原始数据
2. `scanner.py` / `strategy.py`
   - 对标的做信号扫描和技术分析
3. `recommend.py` / `theme.py`
   - 生成每日推荐池
   - 完成题材热度、龙头识别、五大战法评分
4. `decision.py`
   - 生成交易计划与持仓建议
5. `reports.py`
   - 导出盘前计划、收盘复盘、工作台报告
6. `broker.py`
   - 生成委托建议、导出执行计划、对接 SDK 桥接
7. `app_qt.py`
   - 将上述链路串成桌面端工作台

结论：

- 业务方向是对的。
- 当前最大风险不在业务能力缺失，而在 UI 入口层过重、方法重复定义过多、状态联动开始变复杂。

## 审计结论

### 1. `app_qt.py` 已经成为主要技术债源头

- 文件体量过大。
- 历史迭代中多次直接覆盖方法，导致同名方法在文件里重复定义。
- Python 最终只执行最后一次定义，因此程序还能跑，但维护时很容易读到“失效旧代码”。

### 2. 推荐页联动逻辑重复

以下逻辑在多个入口中重复出现：

- 当前题材筛选下的推荐池行过滤
- 根据 `stock_id` 在推荐池中定位行
- 同步切换战法明细

这类逻辑如果继续复制，后面接更多面板和提醒链时会越来越难维护。

### 3. 文案、页签名、战法名重复散落

- 工作区页签
- 五大战法名称
- 战法评分字段映射

这些都属于“配置级信息”，应该集中，而不是散落在各个方法里。

## 本轮重构

### 1. 抽出推荐页联动公共方法

新增并统一使用以下公共方法：

- `_filtered_daily_pool_rows()`
- `_set_strategy_detail_from_row()`
- `_select_daily_pool_row_by_stock_id()`

收益：

- `龙头榜 -> 推荐池`
- `交易计划 -> 推荐池`
- `持仓建议 -> 推荐池`

三条联动链不再各写一套查找逻辑。

### 2. 修复主线推演路径显示问题

- 之前主线推演路径里，主线题材有机会直接显示对象文本而不是题材名称。
- 本轮统一改为显示 `theme_name`。

### 3. 抽出跨页面常量

新增统一常量：

- `WORKSPACE_TAB_LABELS`
- `STRATEGY_FILTER_LABELS`
- `STRATEGY_SCORE_FIELDS`
- `STRATEGY_WORKBENCH_SPECS`

收益：

- 后续改页签名、加战法、改映射，不需要在多个 UI 方法里逐个翻。

## 为什么这轮不直接大拆 `app_qt.py`

虽然 `app_qt.py` 已经足够大，理论上应该拆分为：

- overview workspace
- recommend workspace
- broker workspace
- shared ui components
- shared workspace controller

但当前项目仍在高频迭代期，直接大拆风险较高：

- 容易打断现有工作链路
- 容易引入 UI 回归问题
- 成本会高于当前阶段收益

因此本轮策略是：

- 先抽重复逻辑
- 先集中配置
- 先修可见问题
- 等交互结构再稳定一轮后，再拆分为多文件工作区模块

## 下一阶段建议

### 第一优先级

- 继续清理 `app_qt.py` 中重复定义的旧方法
- 明确只保留一套最终生效的工作区构建函数

### 第二优先级

- 将首页、推荐页、交易页拆成独立 workspace builder
- 将卡片组件与表格联动提炼为共享 UI 层

### 第三优先级

- 将“提醒链、状态栏、页面路由、联动选择”收敛为统一控制器
- 为未来插件化或多数据源切换做准备

## 验收标准

- 项目主业务链条能够被清晰描述。
- 重复的推荐页联动逻辑被收敛。
- 常量配置不再散落多处。
- 当前功能、测试与导出链路不回退。
