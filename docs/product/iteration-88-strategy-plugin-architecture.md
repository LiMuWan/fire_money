# Iteration 88: 战法插件化架构

## 目标

把“战法”从当前的固定注册表配置，推进到“可扩展算法单元”：

- 现有内置战法继续可用。
- 新增战法不再必须改死在主代码里。
- 后续支持用户自定义战法。
- 配置中心继续承担 JSON 战法的增删改。
- 脚本型战法通过目录发现和重载接入。

## 当前问题

现有项目已经有战法配置中心和 `strategy_catalog.json`，但本质仍是：

- 战法元数据可编辑。
- 打分逻辑主要还是固定公式权重。
- 想新增“真正的算法型战法”时，仍要改 Python 主代码。

这意味着“可配置”已经具备，但“可插拔”还不完整。

## 方案 A

继续保留 `Python + Qt` 主体，不做技术栈迁移。

### 一阶段目标

- 把战法抽象成两类来源：
  - `catalog`：来自 `strategy_catalog.json` 的 JSON 战法。
  - `script`：来自 `quant_hunter/strategy_plugins/` 目录的脚本战法。
- 注册表在运行时同时加载两类战法。
- 脚本战法可提供自定义 `compute_score(...)`，不受固定公式权重限制。
- 配置中心能看见脚本战法，但按只读处理。

### 为什么先这样做

- 风险低，不破坏现有推荐链路。
- 能马上验证“脚本战法”是否满足业务。
- UI 不需要先做复杂的脚本编辑器，就能支持扩展目录。
- 后续用户自定义，也有稳定落点。

## 目录结构

### 1. JSON 战法目录

- 路径：`quant_hunter/strategy_catalog.json`
- 用途：配置型战法，支持在 UI 里新增、修改、删除、导入导出。

### 2. 脚本战法目录

- 路径：`quant_hunter/strategy_plugins/`
- 用途：算法型战法，支持目录发现和重载。
- 约定：只扫描不以下划线开头的 `*.py`。

## 脚本战法契约

每个脚本至少提供：

```python
STRATEGY_DEFINITION = {
    "name": "量价突破",
    "score_field": "volume_breakout_score",
    "description": "抓放量突破、承接确认和二次加速",
    "formula_stage": "base",
}
```

可选提供：

```python
def compute_score(context, *, dependency_scores=None, definition=None):
    ...
    return 76.5
```

### 参数约定

- `context`
  - 当前推荐计算上下文，已经做过标准化。
- `dependency_scores`
  - 已经完成计算的其他战法得分，可用于聚合或依赖型脚本战法。
- `definition`
  - 当前战法定义对象。

### 设计原则

- 有 `compute_score` 时，优先走脚本算法。
- 没有 `compute_score` 时，仍按公式权重算分。
- 脚本战法继续复用现有 UI 元数据、计划默认值和排序链路。

## 配置中心行为

### JSON 战法

- 可在 UI 中新增、复制、修改、删除、导入、导出。

### 脚本战法

- 在列表中可见。
- 编辑区展示脚本战法的规范化元数据快照。
- `保存战法` / `删除战法` 自动禁用。
- 状态栏明确提示来源路径和“只读”属性。
- 修改方式是直接编辑脚本文件，再点击 `重载`。

## 已落实内容

### 注册表层

- `strategy_registry` 已支持：
  - 目录发现脚本战法
  - 脚本加载诊断
  - `catalog` / `script` 来源区分
  - 运行时脚本计分

### UI 层

- 配置中心已支持：
  - 混合显示 JSON 战法和脚本战法
  - 左侧列表来源标识：`[JSON]` / `[脚本]`
  - 区分来源
  - 对脚本战法启用只读保护
  - 重载后展示脚本诊断信息
  - 一键打开当前战法来源文件
  - 一键生成脚本战法模板

### 二阶段已补的操作入口

- `脚本模板`
  - 从配置中心直接生成脚本骨架到 `strategy_plugins/`
  - 生成后自动重载并选中新脚本战法
- `看源文件`
  - JSON 战法打开 `strategy_catalog.json`
  - 脚本战法直接打开对应 `*.py`

### 三阶段已补的操作入口

- `转脚本`
  - 直接基于当前 JSON 战法草稿生成脚本模板
  - 默认把当前元数据、计划参数和公式权重一起带入脚本
  - 生成后可在脚本里继续改 `compute_score(...)`

- 来源筛选
  - 列表支持 `全部来源 / 仅 JSON / 仅脚本`
  - 便于在目录战法和脚本战法同时存在时快速定位

- 脚本诊断面板
  - 配置中心左侧新增脚本诊断区
  - 重载后会显示加载失败、元数据错误和脚本问题
  - 当前已按级别分组展示 `错误 / 警告 / 信息`
  - 可按选中诊断项打开对应报错源文件
  - 支持双击诊断项直接打开源文件

- `脚本模板`
  - 当前已经优先走战法向导
  - 不再只依赖名称输入
  - 可把向导里填的名称、简介、阶段、风险和定位一并带入脚本模板

- 脚本能力声明
  - 模板里会生成 `STRATEGY_CAPABILITIES`
  - 当前支持：
    - `required_context_keys`
    - `dependency_strategy_names`
    - `allow_dependency_scores`
    - `notes`
  - 转脚本时会优先根据现有公式权重自动推导默认能力声明
  - 已进入配置中心表单，可直接编辑并随 JSON 草稿流转

- 配置中心表单
  - 当前已经补进脚本能力声明字段：
    - 脚本上下文：结构化可勾选列表
    - 脚本依赖：结构化可勾选战法列表
    - 是否允许读取依赖得分
    - 脚本备注
  - 当前已支持字段级提示：
    - 未知上下文字段会直接提示在“脚本上下文”附近
    - 非法依赖或依赖配置问题会直接提示在“脚本依赖”附近
  - 当前已支持依赖列表直接禁选：
    - 当前战法自己
    - 基础战法场景下的聚合战法
  - 禁选项会直接显示原因标签，而不只是灰掉
  - 当前已支持“按公式自动推导能力声明”按钮
  - 自动推导后会直接把“脚本上下文 / 脚本依赖”结果回写到表单，并同步状态提示
  - 这些字段会一起参与：
    - JSON 草稿保存
    - JSON -> 脚本模板生成
    - 脚本帮助文本展示

- 静态安全边界
  - 当前会在脚本执行前做 AST 静态检查
  - 当前会拦截：
    - 不在白名单内的 import
    - 顶层副作用语句
    - 非 `STRATEGY_DEFINITION / STRATEGY_CAPABILITIES` 的顶层赋值
    - 危险 import（例如 `os`）导致的脚本直接执行
  - 当前 import 白名单：
    - `__future__`
    - `math`
    - `statistics`
    - `typing`

- 配置页摘要卡
  - 当前已新增“脚本能力”摘要卡
  - 会显示当前选中战法的来源、能力声明摘要和诊断数量
  - 入口直接跳到脚本诊断区
  - 当前也会显示错误/警告数量，方便第一屏判断是否存在阻塞
  - 当前点进“脚本能力”时会优先切到 `仅错误` / `仅警告` 筛选
  - 当前会优先展示最近一次自动推导出来的上下文/依赖数量

- 配置状态联动
  - 表单层一旦出现脚本能力声明错误
  - `config_status_banner` 会直接切到 `阻塞待处理`
  - 不再要求用户先重载再去诊断区确认问题

### 当前交互约束

- JSON 战法
  - 可以新增、复制、保存、删除。
  - 可以继续导出、导入。
  - 可以进一步转成脚本模板。
- 脚本战法
  - 在列表中展示为 `[脚本] 战法名`
  - 在编辑区展示其规范化元数据快照
  - `保存战法` / `删除战法` 自动禁用
  - 修改方式是直接编辑脚本，再点 `重载`
  - 可以通过 `看源文件` 直接打开对应脚本
  - 若加载失败，会在脚本诊断区显示，并可按选中诊断项打开对应报错源
  - 当前已支持加载时做基础静态校验：
    - 未知上下文字段
    - 基础脚本声明聚合依赖
    - 依赖声明与 `allow_dependency_scores` 不一致
    - 无能力声明时给出信息级提示
    - 危险 import（如 `os`）直接阻断加载

### 示例

- `quant_hunter/strategy_plugins/_example_volume_breakout.py`
  - 作为脚本战法样例存在。
  - 默认以下划线开头，不会自动激活。
  - 复制或改名后可接入。

## 后续计划

### 二阶段

- 给配置中心增加“从脚本模板复制当前 JSON 战法”的辅助入口。
- 在列表中增加来源筛选：全部 / JSON / 脚本。
- 对脚本战法补充更明确的诊断面板，而不是只放在状态栏里。

### 三阶段

- 引入脚本战法的能力声明：
  - 是否允许依赖其他战法
  - 是否允许聚合
  - 是否允许访问特定上下文字段
- 给脚本战法增加更严格的静态校验和错误提示。
- 给脚本诊断面板增加更细的错误类型聚合和直接定位到“当前选中诊断项”的能力。
- 把脚本能力声明展示到配置中心专门的摘要区，而不只附着在公式帮助文本里。

### 四阶段

- 支持用户自定义战法包。
- 支持导入独立战法脚本目录。
- 支持团队共享战法包和版本管理。

## 风险和约束

- 脚本战法本质上是运行时代码，风险高于 JSON 配置。
- 目前默认信任本地脚本目录，不做沙箱执行。
- 如果后续开放给终端用户，需要补：
  - 权限边界
  - 更严格的脚本校验
  - 发布/签名/版本管理机制

## 当前结论

现阶段最合理的做法不是换技术栈，而是在现有项目里先把“战法插件化”做扎实。

这样能先把扩展性问题真正解决，再决定后面是否需要进一步重构 UI 或迁移前端。
